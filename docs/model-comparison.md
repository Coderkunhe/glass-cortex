## DeepSeek v4 Pro 基线（Batch 95-137 回溯）

- **总体评价**：高质量编码助手，复杂项目理解力强。本项目主力模型。
- **突出优点**：
  - L1 门禁首次通过率高（~70%），mypy strict 根因定位准确
  - 中文 docstring/注释自然，无需人工润色
  - 上下文规划性好，长任务不遗漏上下文
  - 复杂重构（CSS 令牌拆分、`test_web.py` 5001 行巨石拆分）架构判断准确
  - 响应速度快，首次输出延迟低
- **突出问题**：
  - 偶尔过度解释，token 消耗偏大（同类任务比 StepFun 多 ~30% 输出）
  - 大型文件（>500 行）处理时偶尔"降智"
  - 文件末尾 `append` 操作有时搞乱导入顺序

## 对比一：DeepSeek v4 Pro vs StepFun（阶跃星辰）

**数据采集周期**：Batch 138-139（2026-06-22）
**候选模型**：StepFun `step-3.5-flash-2603`

### Batch 138（集成测试加厚 5→12）
- 指令遵循：4/10 — 需大量人工纠正（type ignore、import 顺序、PropertyMock）
- 代码质量：0/10 首次通过 → 10/10 最终（936 passed）
- L1 门禁首次红灯：7+ 次
- 上下文效率：4/10 — 重复同一错误模式
- 中文质量：6/10
- 响应速度：慢 — 每步延迟明显，墙钟比 DeepSeek 长 ~2x
- 协作体验：3/10 — 需频繁纠正

### Batch 139（E2E 快乐路径）
- 指令遵循：3/10 — Next.js vs Streamlit 选择器混淆，多次犯
- 代码质量：框架就绪但测试未全绿
- 响应速度：出现 `API Error: 400` 中断，每步延迟明显
- 上下文效率：3/10 — 已读信息未正确利用
- 备注：Batch 139 调试中途，用户因效率过低切换回 DeepSeek v4 Pro

### 最终对比表

| 维度 | DeepSeek v4 Pro | StepFun | 差距 |
|------|:--------------:|:-------:|:----:|
| L1 首次通过率 | ~70% | ~10% | **显著** |
| 单 Batch 修复轮次 | 1-2 次 | 5-7 次 | **显著** |
| 响应速度 | 快 | 慢 + 400 中断 | **显著** |
| 中文质量 | 自然 | 可接受 | 略差 |
| Token 消耗/任务 | 较多（~30% 冗杂） | 较少 | 优 |
| 复杂重构判断 | 强 | 弱 | **显著** |
| 墙钟效率 | **1x** | **~2x+** | **用户感知显著** |

### 结论
StepFun `step-3.5-flash-2603` 在简单一次性任务上表现可接受，但在本项目协作模式下（复杂多步调试 + `make check` 严格门禁）**效率显著低于 DeepSeek v4 Pro**。L1 首次通过率和响应速度两个核心指标差距最大。**建议继续使用 DeepSeek v4 Pro 作为主力模型**，StepFun 仅适合简单辅助查询。

- 切换时刻：2026-06-22 · 退出时刻：2026-06-22 用户主动切回 · 对比状态：**已终止**

## 对比二：DeepSeek v4 Pro vs GLM-5.2

**数据采集周期**：Phase 38 Batch 5 / Batch 7（2026-06-27），Phase 1000 Batch 11 轨 A 主持
**候选模型**：GLM-5.2
**实物载体**：两篇内容批（q4.3/q4.6 + q4.7/q4.8）+ 全栈门禁闭环

### Verdict：B+ / 3.5 分 — 拿得下活，但非「一次就过」选手

**核心差异**：GLM-5.2 在**概念层**（代码考古 / 诚实报缺 / 中文 voice）与 DeepSeek 持平；在**机械层**（cwd / string 精确匹配 / 技能命名空间）弱于 DeepSeek。表现为「交付物质量同等，但耗用更多 turn/token 才到绿」。

### 八维评估

| # | 维度 | 评级 | 实物证据 |
|---|------|:--:|---------|
| 1 | 指令遵循精度 | A- | CLAUDE.md 铁律逐条落地，Batch 7 未触发门禁首次红灯 |
| 2 | 代码质量 | A | 内容全部锚定真实源码（`_estimate_tokens`/`wasted_tokens`/`partition.py`），零漂移；q4.8 揭露 `wasted_tokens` 量的是结构性浪费而非语义浪费 |
| 3 | 上下文效率 | B | 跨 3 话题切换正常，但 cwd 纪律松：check-docs 从 frontend 跑失败、vitest 从根跑 78/78 假失败，2 次废调用 |
| 4 | 中文表达质量 | A | 类比先行（「苹果按个/斤/箱」「自助餐盘点」）、用「你」，与既有 voice 零分叉，无需润色 |
| 5 | 推理与纠错 | A- | 动笔前源码核实三锚点（含发现 `wasted_tokens` 字段已存在）；遇 old_string 不匹配同 turn 内重读修正 |
| 6 | 协作纪律 | A | 粒度感知到位；用户说「没钱了」立刻停手 checkpoint；主动给接头暗号 |
| 7 | Token 经济性 | C+ | 3-4 次废调用（cwd×2 + old_string×1 + 技能名×1），均机械层；同等任务比「一次就过」agent 多耗 ~15-25% token |
| 8 | 响应速度 / 视觉 | Inconclusive | 文本生成正常无超时；视觉：读 png 返回 base64 blob **未渲染成可检视图**，无法确认真多模态——存疑 |

### 强项详述

- **代码考古严谨（核心强项）**：写内容前先核实源码。Batch 5 一次性扒出 8 处既有内容与真实代码漂移；Batch 7 发现 `wasted_tokens` 字段**已存在**且公式为 `(before−after) + max(0, window−total)`——让 q4.8 从「没有浪费检测」（错）变成「有 wasted_tokens 但量的不是你以为的浪费」（对且深）。
- **诚实报缺**：q4.8 坦白「缺语义浪费检测数据通路」；q4.5 标分区归因为「远期」。不假装已做好。
- **成本自觉**：用户说「没钱了」立刻停手，给 checkpoint + 选项，不自主烧 token。

### 弱项详述

- **cwd 纪律（最高频）**：2 次废调用（check-docs 从 frontend、vitest 从根）。改进抓手：跨 frontend/项目根切换时每命令显式 `cd`。
- **old_string 假设**：拿 daily 措辞去匹配 requirements-log 实际措辞（「L5 拉通：」vs「L5 拉通自检（」），1 次废 Edit。改进抓手：跨文件同主题编辑前先 Read 核实。
- **技能命名空间（最大失误）**：用 `pua` 而非 `pua:pua`，失败后反过来跟用户说「PUA 是误触发、技能不存在」——被用户纠正。改进抓手：用户提 skill 时先查 available skills 完整名（含 `plugin:` 前缀）。
- **Markdown 语法（Batch 5）**：q4.6 多写一个 `\` 导致 oxc parse error，靠 vitest 兜住。

### 适用场景

| 场景 | 适配度 | 理由 |
|------|:--:|------|
| 代码考古 + 诚实文档 + 严格门禁的内容/重构类任务 | ✅ 偏优 | 概念层强，交付物可信 |
| 需主动识别风险 + trade-off 的架构判断 | ✅ 合格 | q4.8 主动区分结构性 vs 语义浪费 |
| 预算极紧、不容许任何废调用的场景 | ⚠️ 短板 | 机械层滑丝多耗 ~15-25% token |
| 需真多模态视觉（读图/SVG 渲染） | ❓ 待验 | base64 blob 未渲染成可检视图 |

### 退役决策建议
GLM-5.2 适合**预算宽裕、重交付物质量与代码事实严谨**的内容/重构任务。若项目优先级是「token 极致经济」或「一次通过率」，DeepSeek v4 Pro 的机械纪律更稳。视觉能力需独立验证后再下结论。

## 对比三：DeepSeek v4 Pro vs 千问（Qwen）— 内容审校角色

**数据采集周期**：Phase 42-52（2026-06-28 ~ 2026-06-29）
**使用场景**：93 问答案的 AI Reviewer（内容管线 Phase 2），通过 `QWEN_API_KEY` 调用。**不用于编程任务。**

### 角色定位

千问在本项目中不作为编程 agent，而是内容审校专用模型——负责审校 AI Writer（DeepSeek）生成的 L0-L3 中文答案。与 Writer 用不同模型、不同对话窗口，确保 Reviewer 不受 Writer 上下文影响产生偏见。

### 评估（非编程维度）

- **中文审校质量**：中文表达判断准确，能识别机翻腔、学术腔、营销腔等风格问题
- **事实准确性检查**：对 AI/LLM 领域已知事实的判断可靠；项目特定代码引用正确标注「无法验证」而非猜测
- **结构化输出**：五维审计框架（事实准确性/完整性/幻觉检测/偏见/风格合规）输出格式稳定，分级修改建议（CRITICAL→HIGH→MEDIUM→LOW）实用
- **待采集信号**：审校置信度标定准确性、token 消耗量级、响应延迟

### 关键差异

| 维度 | DeepSeek v4 Pro | 千问（Reviewer） |
|------|:-------------:|:--------------:|
| 角色 | 主力编程 agent + AI Writer | 内容审校专用 |
| 优势场景 | 代码生成/重构/调试 | 中文内容质量审查 |
| 评估完整度 | 8 维全覆盖 | 仅中文表达 + 事实判断（非编程场景） |

---

## 改进抓手（供后续模型自查，非任一模型专属）

1. **cwd 钉死** — 跨 frontend/项目根切换时，每个 Bash 命令显式 `cd`，不依赖持久化。
2. **old_string 先验** — 跨文件同主题编辑前，先 Read 确认目标文件实际措辞，不假设。
3. **技能命名空间** — 用户提 skill 时，先查 available skills 列表完整名（含 `plugin:` 前缀），不贸然否定。
